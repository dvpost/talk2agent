# Модульность по ответственности

## Модульность по ответственности без переусложнения (MODULAR BY RESPONSIBILITY, SIMPLE BY DESIGN)

**Обязательный принцип:** прямолинейный путь выполнения **внутри** компонента совместим с содержательной декомпозицией **между** компонентами. Простота означает минимум концептуальной сложности для понимания и безопасного изменения кода, **а не минимум файлов и не максимум абстракций**. Правила действуют для модулей, пакетов, функций, классов, обработчиков, сервисов и скриптов пропорционально масштабу проекта.

### Ответственность, связность, границы

- **ОБЯЗАТЕЛЬНО:** у компонента есть понятная основная ответственность; его содержимое связано общей задачей и преимущественно изменяется по общей причине. Несколько функций в одном файле допустимы, когда они образуют единый связный механизм.
- **ОБЯЗАТЕЛЬНО:** различать транспорт и входные точки (HTTP/CLI/consumer), предметные правила, доступ к данным и внешние интеграции, **когда у них действительно отдельные причины изменения**. Не создавать по одному обязательному слою на каждую техническую операцию.
- **ОБЯЗАТЕЛЬНО:** зависимости между модулями и направление их использования должны быть ясны. Обращение к внутренней реализации соседнего модуля в обход его контракта, циклические зависимости и скрытое изменение чужого состояния — повод для исправления или фиксации несоответствия.
- **ЗАПРЕЩЕНО:** добавлять в уже крупный «универсальный» файл новую несвязанную область поведения только ради удобства агента или экономии файлов. Недопустимы *god object*, *god module*, монолитные обработчики, объединяющие множество независимых обязанностей, и дублирующие «центральные» utility-каталоги без конкретных владельцев ответственности.
- **РЕКОМЕНДУЕТСЯ:** держать связанные элементы близко: код, соответствующие тесты и интерфейс модуля должны легко находиться; название и структура каталогов должны помогать новому агенту найти нужную реализацию без чтения всего проекта.

### Когда выделять модуль, компонент или функцию

**Разделить код ОБЯЗАТЕЛЬНО в рамках новой работы**, если без декомпозиции возникают несколько устойчиво независимых ответственностей и это можно сделать с контролируемым риском и без несогласованного изменения контрактов. Типовые сигналы:

1. Функция или файл одновременно реализует, например, HTTP-транспорт, существенные бизнес-правила, SQL-запросы и внешние SDK, и эти части имеют разные причины изменения.
2. Чтобы исправить локальный бизнес-сценарий, приходится постоянно читать, тестировать или менять несвязанные части файла.
3. Несколько логических областей конкурируют за общую изменяемую область состояния, а границы и инварианты неочевидны.
4. В одном месте накапливаются независимые ветви поведения и зависимости, которые можно разделить без распыления общей логики.
5. Общий бизнес-инвариант реально дублируется и разные копии способны разойтись; тогда требуется единый канонический владелец этой логики.

**Не является самостоятельным основанием для дробления:** фиксированное число строк, длина имени файла, наличие двух небольших функций, один раз встретившийся повтор, предположительное будущее переиспользование или абстрактная рекомендация «сделать архитектуру чище». Универсальный предел строк, количества методов или глубины вложенности **не устанавливается**. Сервис может использовать собственные пороги как диагностические сигналы, но они не заменяют анализа ответственности.

### Запрет искусственной модульности

- **ЗАПРЕЩЕНО:** строить интерфейс + фабрику + адаптер + сервис + фасад для единственной тривиальной операции без реального контрактного, тестового или архитектурного основания.
- **ЗАПРЕЩЕНО:** создавать однофункциональные модули, обёртки без поведения, «универсальные» расширяемые платформы, speculative plugins и абстракции под неизвестные будущие требования только ради формального разделения кода.
- **РЕКОМЕНДУЕТСЯ:** предпочитать простые функции и компактные предметные модули; вводить общий компонент при **действительном** совместном использовании либо при необходимости централизованно защищать один инвариант. Повторяющаяся пара строк не всегда требует утилиты.
- **ОБЯЗАТЕЛЬНО:** избегать «логической нарезки», когда путь от входа до результата проходит через цепочку бессодержательных делегирующих файлов. Если декомпозиция ухудшает читаемость и навигацию, объединить части.
- **НЕ ПУТАТЬ:** разделение ответственности с добавлением retry/fallback. Чёткие границы модулей не разрешают запасные пути, обёртки ради гипотетических отказов или скрытие ошибок: требования [«Прямолинейное исполнение»](execution-paths.md) и [«Реестр исключительных путей»](exceptional-execution-paths.md) продолжают действовать.

### Рефакторинг и сохранение поведения

- Новую функцию размещать в правильной существующей подсистеме; выделять новый модуль **только при возникновении содержательной границы**.
- При небольшом безопасном улучшении структуры в границах текущей задачи допустима локальная декомпозиция при наличии релевантных тестов и без изменения внешнего поведения. Не смешивать большой рефакторинг с функциональным изменением, если это мешает проверить результат.
- Если для устранения большого смешанного модуля требуется массовое перемещение кода, перестройка DI/интерфейсов, миграция состояния или меняются внешние контракты, нужен **отдельный явно разрешённый проект работы**. Его план и все открытые предложения хранятся **только в `TODO/`**.
- При аудите уже существующего сервиса **ЗАПРЕЩЕНО** автоматически распиливать все длинные файлы. Сначала определить реальные обязанности, связанность, зависимости, тестовое покрытие и риск; небезопасные/несогласованные улучшения оформить только в `TODO/`.
- Рефакторинг должен сохранять действующее поведение, формат ошибок, безопасность, наблюдаемость и производительность, если иное не согласовано. Сохранять регрессионные тесты и проверять интеграционные контракты на затронутых границах.

### Механическая проверка там, где это оправдано

- Для существенной архитектуры **РЕКОМЕНДУЕТСЯ** автоматическая проверка разрешённых направлений зависимостей, запрещённых импортов, циклов между пакетами и критичных границ через имеющиеся в стеке линтеры, dependency tests или CI.
- Ограничение размера файла или сложности функции может быть **предупреждением** для ревью, но само по себе не доказывает плохую архитектуру и не должно заставлять агента создавать бессмысленные файлы.
- После декомпозиции проверить: ни один публичный контракт не изменён случайно; компоненты имеют ясных владельцев ответственности; не появились бесполезные промежуточные слои; соответствующие тесты проходят; `docs/ARCHITECTURE.md`/`docs/modules/` **описывают только реально существующую новую структуру**.
- Изменение **организации кода само по себе не является** exceptional execution path и не заносится в `docs/exceptional_execution_paths.md`. Реестр используется только для действующих спорных **путей выполнения** согласно [«Реестр исключительных путей»](exceptional-execution-paths.md).

**Практический критерий:** будущему агенту должно быть достаточно найти ответственную подсистему, понять её контракт и прочитать ограниченный набор связанного кода, чтобы безопасно изменить поведение; при этом выполнение сценария остаётся прозрачно прослеживаемым без искусственной цепочки обёрток.

**Основания принципа:** [OpenAI — Harness Engineering](https://openai.com/index/harness-engineering/), [Anthropic — Building Effective Agents](https://www.anthropic.com/engineering/building-effective-agents), [Google — Code Review Practices](https://google.github.io/eng-practices/review/reviewer/looking-for.html). Конкретные требования этого справочника — правила внутреннего стандарта, а не дословная универсальная архитектура этих компаний.
